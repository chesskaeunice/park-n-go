# Park n Go development roadmap

**Current status (31 October 2026):** Phases 1–7 are implemented in local development. Phase 7 adds permissioned admin operations, reconciliation, refund approval with provider confirmation, prospective pricing, reports with CSV/PDF export, and an append-only admin audit trail (see `PHASE_7.md`). Maya Sandbox checkout, server-side retrieval, signed webhook handling, reservation confirmation, local QR image generation, QR entry/exit, the facility-scoped Exit Kiosk, overtime settlement with 15-minute exit grace, and parking extensions are available and pass deterministic mocked-provider tests (see `PHASE_6.md`). Live Maya Sandbox verification of overtime and extension payments, production credentials, deployment (including migrations 006–007 on `parkngo_db`), receipts/refunds, physical-device checks, and operational reporting remain outstanding.

Native PHP 8.2+, MySQL `parkngo_db`, PDO, server-rendered HTML, CSS, and JavaScript. No framework or Node backend. Each phase ends with implementation notes, changed files, XAMPP instructions, feature checks, and outstanding work.

CIT 305 historical planning notes are retained below. The active provider implementation is Maya Sandbox, not PayMongo.

Design refinement (29 October 2026): the current interface uses Light Midnight Electric with white/gray surfaces and restrained indigo accents. This presentation-only change preserves Phase 2 behavior and does not advance the roadmap. See `DESIGN_REFINEMENT.md` for the changed files and desktop/mobile browser checks.

1. **Setup and responsive UI — implemented.** Public PHP routing and layouts; original Midnight Electric branding; homepage, about, process guide, searchable illustrative facilities, floor-switching map, account availability notices, and 404 page. No operational data or accounts yet.
2. **Database and identity — implemented.** Versioned normalized MySQL schema and development seeds; environment loader; PDO connection; secure sessions, registration/login/logout, role middleware, CSRF, database rate limits, profile editing, and single-use password resets. Registration always creates drivers. Local reset messages use a private outbox; external delivery requires configured and verified mail infrastructure. See `PHASE_2.md`.
3. **Parking inventory — implemented and tested.** Database-backed facility search/details and active floors; time-window availability through a read-only JSON API and Fetch; server-rendered no-JavaScript selection fallback; refresh/error handling; protected facility/floor/slot create/edit/disable operations with audit logs and commitment checks. No schema changes or data resets required. See `PHASE_3.md`.
4. **Reservations — implemented and tested.** Server-reviewed estimates and policy snapshots, idempotent pending checkout, ten-minute holds/expiry, owner history/cancellation, and facility/floor/slot locking with current conflict reads. Independent PHP/MySQL races verify overlapping requests, repeated keys, non-overlapping boundaries, and admin-disable competition. Additive migration preserves existing records. Payment, confirmation, receipts, and QR issuance remain disabled until their phases. See `PHASE_4.md`.
5. **QR tickets, scans, and parking sessions — implemented locally.** Local QR generation, random opaque tokens, hash storage, authorized attendant facility checks, entry/exit windows, replay prevention, manual-code assistance, sessions, and overtime calculation are implemented. Camera testing needs HTTPS or localhost and a physical device. Overtime settlement and extensions are implemented in Phase 6; see `PHASE_6.md`.
6. **Maya REST integration and payments — implemented in Sandbox.** Maya hosted checkout, server-side credentials, payment retrieval, signed webhook verification, reconciliation/deduplication, local confirmation, and QR eligibility are implemented. Actual Sandbox retrieval has been exercised; deterministic mocked provider tests cover success, failure, cancellation, pending, mismatch, outage, duplicate, and replay cases. Receipts/refunds and production credentials remain out of scope for this local phase.
7. **Operations — implemented locally (see `PHASE_7.md`).** Role-protected driver, attendant, and admin dashboards; management of users, attendants, inventory, rates, reservations, sessions, transactions, notifications, and audit logs. Chart.js analytics with exports and date filters.
8. **Integration testing, evidence, and deployment.** Run at least five actual integration scenarios, Postman or equivalent API tests, end-to-end and simultaneous booking tests, payment callback and QR replay tests, actual camera and mobile checks; finish architecture/integration documentation, security/deployment HTTPS, secrets, backup/restore, log hygiene, expiry jobs, and production configuration review. Preserve sanitized real provider evidence; do not label plans or fixture payloads as completed integration.

## Phase 1 implementation boundary

Public content is served through PHP and search is handled server-side. The map is a client-side interaction with conspicuously labeled illustrative inventory. Selection does not persist or create a hold. No sign-in forms collect credentials before authentication exists. Prices are sample initial-hour prices, not calculated booking estimates. Account pages explain availability rather than presenting dead submit buttons. Driver bottom navigation belongs with authenticated pages in Phase 2 onward.

## Database relationships (implemented in Phase 2)

`parking_facilities → parking_floors → parking_slots`; `users → reservations → reservation_holds / qr_tickets / parking_sessions`; `parking_facilities → parking_rates`; `reservations → payment_attempts → payment_attempt_events`; users and relevant records link to `notifications`, `qr_scan_logs`, and `audit_logs`. Migrations 001–005 preserve the existing schema while adding Maya attempts, redirect data, session timing, QR status/manual-code fields, and attendant-facility authorization.
